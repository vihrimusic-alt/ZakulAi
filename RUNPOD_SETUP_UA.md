# ZaKul RunPod Queue v1 — перший запуск генератора без сайту

Це **додаток до ACE-Step**, підготовлений за надісланим `ACE-Step-1.5-main.zip`.
Він додає окремий Queue-воркер. Старі `Dockerfile`, API, UI та локальні скрипти
не змінені. У комплекті немає ваг моделей або ключів.

## Що вже реалізовано, а що ні

- RunPod `Queue` з `handler.py`; один GPU-запит одночасно.
- Генерація з опису та готового тексту, інструментал; один або два послідовні варіанти.
- Явна тривалість `duration_seconds`: 0.1–240 с. Для коротших за 10 с кліпів модель
  генерує щонайменше 10 с, після чого результат обрізається. Це не робить обчислення
  пропорційно дешевшими за 10-секундну генерацію.
- MP3 320 кбіт/с для прослуховування; у режимі S3 також FLAC без втрат.
- Неправильні запити відхиляються до завантаження моделей. Немає тихого запуску на CPU.
- Завантажені моделі повторно використовуються, поки живе воркер.

**Це лише перший етап, не повне перенесення ZaKul Studio.** Сайт, його черга,
авторизація, база, бібліотека, Copilot, аналіз аудіо, ремікси та голосові профілі
цим архівом не підключаються. Старий `local-worker.mjs` не сумісний із новим Queue API
простою заміною URL. Після тесту генератора потрібен окремий адаптер сайту.

Точне дотримання тембру сопілки, лише двох інструментів, дикції чи якості вокалу
не гарантується успішним виконанням запиту: це перевіряємо прослуховуванням.

## 1. Додати файли в GitHub

1. Розпакуй додаток `ZaKul_RunPod_Queue_v1.zip` на комп'ютері.
2. Відкрий свій репозиторій `vihrimusic-alt/ZakulAi`.
3. Створи гілку **`runpod-queue-v1`** від `main`: у списку гілок введи нову назву
   і вибери створення гілки. Це збереже старий запуск у `main`.
4. На новій гілці обери **Add file → Upload files**. Перетягни **вміст**
   розпакованої папки в корінь репозиторію, не ZIP і не зовнішню папку:
   `handler.py`, `Dockerfile.runpod`, `Dockerfile.runpod.dockerignore`,
   `zakul_runpod/`, `test-runpod.ps1`, `RUNPOD_SETUP_UA.md`.
5. Збережи зміни на цій гілці. Поруч мають залишитися старі `Dockerfile`,
   `pyproject.toml`, `uv.lock`, папки `acestep/` та `openrouter/`.

Не замінюй наявний репозиторій усім архівом ACE-Step з іншого джерела:
це може прибрати попередні власні виправлення. Додаток додає лише свої файли.
Якщо в репозиторії вже є власний кореневий `handler.py`, спочатку порівняй його
на новій гілці. Перевірка API під час Docker-збірки зупинить відомі несумісності
з іншим знімком ACE-Step до запуску генерації, але не замінює GPU-тест.

## 2. Поточний екран RunPod

Після завантаження коду повернись до **Deploy from a GitHub repository**:

| Поле | Значення |
| --- | --- |
| Repository | `vihrimusic-alt/ZakulAi` |
| Branch | `runpod-queue-v1` |
| Dockerfile path | `/Dockerfile.runpod` |
| Endpoint type | **Queue**, не Load balancer |

Шлях `/Dockerfile` тут не підходить: він запускає старий UI/API.
Не додавай `/ping`, `/health`, порти 8001 або `cloudflared` — цей воркер
обробляє завдання через RunPod SDK, а не через публічний HTTP-сервер.
Якщо нова гілка ще не показується, онови сторінку після збереження GitHub.

Після цих налаштувань можна натиснути **Next**. До **Deploy** перевір налаштування
GPU та ліміт воркерів; для першого запуску бажано показати цей екран у чаті.

## 3. Рекомендовані налаштування першого тесту

| Поле | Початкове значення |
| --- | --- |
| Name | `zakul-queue-v1` |
| GPU | один GPU з 24 ГБ VRAM, наприклад доступний L4 / A5000 / RTX 3090 |
| GPUs per worker | `1` |
| Active workers / Minimum | `0` |
| Max workers | `1` |
| Idle timeout | `5` секунд |
| Execution timeout | `1800` секунд |
| FlashBoot | увімкнений |
| Container disk | орієнтир `50 GB`, якщо поле доступне |
| Container start command | порожньо: використати CMD з Dockerfile |

Це стартовий профіль **2B Turbo + 0.6B LM**, як у попередньому Fast-режимі,
але без ноутбука. Модель XL зараз не вмикаємо. Фіксований backend LM — `pt`,
без обов'язкових FlashAttention/INT8/torch.compile. Інші моделі зі списку у
`config.py` потребують окремого тесту VRAM і якості; їх підтримка не є бенчмарком.

Нуль Active workers не означає безкоштовний сервіс: запуск, завантаження моделей,
обчислення й час до вимкнення воркера оплачуються. Max=1 обмежує паралельність,
але не встановлює місячний ліміт витрат. Сховище оплачується окремо.

### Диск моделей

Для багаторазових тестів можна приєднати **Network Volume 50 GB**. Спочатку звір
наявність вибраного GPU в регіоні диска: том обмежує вибір регіону. Не купуй том
у випадковому регіоні. Стандартне монтування Serverless — `/runpod-volume`;
воркер автоматично зберігатиме ваги в `/runpod-volume/checkpoints`.

Без тома вони будуть у `/app/checkpoints`, і після заміни контейнера можуть
завантажуватися знову. FlashBoot не є гарантією постійного зберігання ваг.
Початковий downloader ACE-Step також завантажує базовий комплект із 1.7B LM;
використовувана за замовчуванням 0.6B LM завантажується окремо. Це причина мати
запас диска, навіть якщо активна модель невелика.

### Змінні середовища

За замовчуванням усе для короткого тесту вже задано. За бажанням явно вистав:

```text
ACESTEP_CONFIG_PATH=acestep-v15-turbo
ACESTEP_LM_MODEL_PATH=acestep-5Hz-lm-0.6B
ACESTEP_OFFLOAD_TO_CPU=false
ACESTEP_LM_OFFLOAD_TO_CPU=false
```

Не перенось старий список змінних Load Balancer. `ACESTEP_NO_INIT`, `PORT`,
`HEALTH_CHECK_PATH`, `ACESTEP_API_URL`, `ZAKUL_SITE_URL` не налаштовують цей адаптер.
Окремий `RUNPOD_API_KEY` у контейнер додавати для обробки Queue-завдань не потрібно:
RunPod передає воркеру власні службові параметри. Ключ клієнта потрібен лише на
комп'ютері або майбутньому сервері сайту, не в браузерному JavaScript.

## 4. Перевірка після завершення Docker-збірки

Наявність коду ще не означає, що endpoint розгорнутий. Дочекайся успішної збірки
в RunPod та скопіюй **Endpoint ID**. За Active=0 відсутність постійного воркера
нормальна: тестовий запит має його запустити.

У розділі **Requests** першим можна надіслати:

```json
{"input":{"operation":"health"}}
```

`cuda_available: true` перевіряє GPU. `models_initialized: false` після цього
очікуване: health не завантажує ваги. Це **не** доказ готовності генерації.

### Завантажити й прослухати перший MP3

У PowerShell перейди в розпаковану папку додатка і виконай:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\test-runpod.ps1 -EndpointId "ТВІЙ_ENDPOINT_ID"
```

Скрипт приховано попросить RunPod API key, зробить **один** запит `/run`, дочекається
завершення та збереже файл у новій папці `runpod-results` поруч зі скриптом.
Це платний тест 20-секундного інструменталу з сопілкою й басом, без LM thinking.
Ключ у файл не записується. Не надсилай його в чат.

Перший запит може тривати значно довше через завантаження ваг. Зразки запитів
дозволяють до **30 хвилин виконання** та мають TTL 1 годину. Не залишай збійний
воркер без нагляду. Перевір журнал, якщо прогрес довго не змінюється.

Для перевірки вокалу та LM:

```powershell
.\test-runpod.ps1 -EndpointId "ТВІЙ_ENDPOINT_ID" -RequestFile ".\zakul_runpod\examples\generate-vocal.json"
```

Для явного завантаження обох моделей без генерації:

```powershell
.\test-runpod.ps1 -EndpointId "ТВІЙ_ENDPOINT_ID" -RequestFile ".\zakul_runpod\examples\warmup.json"
```

`Ctrl+C` зупиняє лише PowerShell, не хмарне завдання. Скасовуй непотрібне завдання
в RunPod. Повторне очікування того самого завдання без створення нової генерації
(час роботи вже запущеного воркера продовжує оплачуватися):

```powershell
.\test-runpod.ps1 -EndpointId "ТВІЙ_ENDPOINT_ID" -JobId "ПОПЕРЕДНІЙ_JOB_ID"
```

Якщо POST `/run` завершився мережевою помилкою, спершу перевір **Requests**:
завдання могло бути прийняте. Скрипт навмисно не повторює POST автоматично.
Результат `/run` зберігається в RunPod обмежений час (зараз 30 хвилин після
завершення): завантаж MP3 відразу. Це не бібліотека постійного зберігання.

## 5. Довгі пісні й постійне зберігання — після короткого тесту

`output_mode: "inline"` повертає сам MP3 у base64, до 60 с на варіант, до двох
варіантів. Файли не залежать від життя контейнера, але результат треба встигнути
забрати. Відповідь не містить локальних `D:\...` або `/tmp/...` URL.

Для довгих пісень використовуй `output_mode: "s3"` і власне S3-сумісне сховище
(наприклад, окремий bucket Cloudflare R2). У Secrets RunPod додай:

```text
ZAKUL_S3_ENDPOINT_URL=https://YOUR_S3_COMPATIBLE_ENDPOINT
ZAKUL_S3_BUCKET=YOUR_BUCKET
ZAKUL_S3_ACCESS_KEY_ID=SECRET
ZAKUL_S3_SECRET_ACCESS_KEY=SECRET
ZAKUL_S3_REGION=auto
ZAKUL_S3_PREFIX=zakul/results
```

Для AWS S3 endpoint можна не задавати; регіон має відповідати bucket. `auto`
підходить R2, але не всім S3-провайдерам. Ключу потрібні права читати/писати
об'єкти лише потрібного bucket/prefix. Для першого inline-тесту ці ключі не потрібні.

У цьому режимі результат містить MP3 та FLAC, `bucket`, `key` і тимчасові підписані
посилання на 1 годину. Для бібліотеки слід зберігати **ключі об'єктів**, а не
використовувати підписане посилання як постійну адресу. Новий сайт має видавати
доступ відповідно до власника пісні. Sites-owned R2 bucket не стає доступним
RunPod автоматично — його підключення/збереження результатів налаштовується окремо.

Операція не повідомляє про успіх, поки файли не завантажені. Якщо завантаження
обірвалося посередині, вже завантажені об'єкти зберігаються під префіксом завдання;
вони не видаляються автоматично. Перед продакшном потрібні політика очищення
незавершених результатів, повернення кредитів та ідемпотентний імпорт у сайт.

## 6. Перевірки для розробника

```bash
python -m zakul_runpod.compatibility
python -m unittest discover -s zakul_runpod/tests -p '*_test.py' -v
docker build --platform linux/amd64 -f Dockerfile.runpod -t zakul-queue:v1 .
```

Для тестів без GPU потрібні `zakul_runpod/requirements.txt` і FFmpeg/FFprobe.
У `compatibility.py` перевіряються потрібні поля/аргументи API ACE-Step без
імпорту Torch. Docker встановлює Linux CUDA-залежності з вихідного `uv.lock`,
використовує його версії як обмеження для залежностей адаптера та перевіряє
фінальні залежності через `uv pip check`.

SDK RunPod зафіксований на 1.7.13: новий 1.12.0 вимагає `tomlkit>=0.15.1`,
що конфліктує з Gradio 6.2.0 (`tomlkit<0.14`) у цьому ACE-Step. Базовий Queue API
використовує тільки `serverless.start` і `progress_update`; UI/HTTP API не змінюємо.

Під час підготовки пройшли **52 тести**, зокрема реальне MP3/FLAC-кодування
синтетичного сигналу, та перевірка контракту API. Локальний запуск справжнього
RunPod SDK також правильно відхилив тестовий запит із нульовою тривалістю до
імпорту моделей. Сумісність залежностей із версіями `uv.lock` перевірена резолвером.
**Docker daemon і CUDA GPU у середовищі підготовки відсутні**:
першу повну Docker-збірку та справжню AI-генерацію потрібно підтвердити на RunPod.
PowerShell-клієнт також потрібно перевірити на твоєму Windows; код не зберігає ключ
та не повторює створення завдання при невизначеному результаті мережевого запиту.
